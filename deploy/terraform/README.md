# InterLock Disposable Cloud Certification

These Terraform roots create bounded, disposable Kubernetes clusters for
certifying one immutable InterLock release on AWS EKS and DigitalOcean DOKS.
They do not contain credentials, create application secrets, or invent database
defaults.

## Release Contract

Both providers require the same five immutable release inputs:

- `release_version`
- `helm_chart_ref`, without tag or digest
- `helm_chart_digest`, as `sha256:<64 lowercase hex characters>`
- `image_repository`, without tag or digest
- `image_digest`, as `sha256:<64 lowercase hex characters>`

The tag-triggered release workflow writes these values to
`release-manifest.json`. The provider-neutral
`deploy/scripts/release/deploy-oci-release.sh` installs the exact chart digest
and overrides the chart with the exact runtime image digest.

## Credential Boundary

- AWS authentication uses the normal provider chain. CI uses GitHub OIDC and an
  environment-scoped `AWS_DEPLOY_ROLE_ARN`; no static AWS key is required.
- DigitalOcean authentication uses `DIGITALOCEAN_TOKEN` from the process
  environment.
- GHCR authentication uses a short-lived `GITHUB_TOKEN` in CI.
- Application credentials are never Terraform variables. Supply a protected
  Helm values file that references pre-created Kubernetes or external Secrets.

Terraform state contains cluster and network metadata. Both roots use a remote
S3-compatible backend configured at `init`: the certification workflow gives
every run its own state key, so a cancelled run's cluster can still be destroyed
later from that key. Keep the state bucket private, versioned and encrypted.

## Required External Dependencies

Before deploying InterLock, the protected Helm values file must identify:

- reachable production-like PostgreSQL and Redis endpoints,
- existing Kubernetes Secrets for database credentials, Admin signing,
  API-key pepper, PostgreSQL listener TLS, and control-database CA,
- an audit spool storage class appropriate for the provider,
- ingress and DNS/TLS settings when external access is part of certification.

On DigitalOcean, managed PostgreSQL and Valkey are created outside Terraform.
The AWS root can create them with `managed_data_tier = true` (off by default,
and off in the certification workflow, which uses an in-cluster data tier):

- a private RDS PostgreSQL instance, encrypted, TLS-only, whose master
  credential is generated and held by Secrets Manager, so it never enters
  state or plans;
- a single-node ElastiCache Valkey replication group with TLS required and an
  AUTH value generated by Terraform. That value is in state, which is why the
  state bucket must be private and encrypted;
- security groups admitting only the cluster's nodes.

The data tier shares the cluster's lifecycle: `terraform destroy` deletes it,
without a final snapshot. Do not enable it for a database you need to keep
beyond the cluster.

The EKS cluster installs the EBS CSI driver (with an EKS Pod Identity role)
and makes its gp3 class the default, so the gateway's audit-spool claim can
bind. Nodes are Spot by default (`node_capacity_type`); a deployment you keep
should use `ON_DEMAND`.

## Local Validation

Run formatting and offline validation after Terraform is installed:

```bash
terraform fmt -check -recursive deploy/terraform
terraform -chdir=deploy/terraform/environments/aws init -backend=false
terraform -chdir=deploy/terraform/environments/aws validate
terraform -chdir=deploy/terraform/environments/digitalocean init -backend=false
terraform -chdir=deploy/terraform/environments/digitalocean validate
```

Provider lock files generated by `terraform providers lock` should be committed
before the first live certification.

## Cost And Teardown

These roots create billable resources. They use bounded autoscaling and tag all
resources as disposable. The cloud certification workflow runs `terraform
destroy` under `if: always()`; operators must still verify teardown in the
provider console after interrupted workflow or runner failure.
